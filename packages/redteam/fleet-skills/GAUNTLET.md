# The Gauntlet — adoption gate for this package

Source: Prompt Pack §6 (`redteam-ultimate-system-prompts-2026-11-01.md`, RedTeam goal files). The gauntlet runs before adoption and re-runs on any change to the prompts, skills, knobs, or the modules in `src/`.

**Adoption rule: this package is NOT adopted until every LIVE item below passes.** The mechanical items in `test/gauntlet.test.ts` are necessary — they prove the harness structure the live runs stand on — and never sufficient. A green mechanical run must never be reported as the gauntlet passing.

Run the mechanical subset with the package test command (`pnpm --filter @secscan/redteam-fleet-skills test`, or `tsc -p tsconfig.test.json && node --test dist-test/test/*.test.js` from this directory). Current mechanical state: 11 gauntlet tests, all passing; 79 tests package-wide, all passing (2026-11-01).

## Known gap the mechanical battery documents — CLOSED 2026-11-01

The battery originally pinned a real gap: `hostInScope` did not implement CIDR ranges, so a record target of `10.0.0.0/24` matched only `10.0.0.0` and range members were denied fail-closed. CIDR support has since landed in the scope guard (IPv4 CIDR entries match by masked network equality, deny-beats-allow applies to CIDR entries too, hostnames never match CIDR entries, IPv6 CIDR remains unsupported and falls through to hostname matching). The battery now asserts the supported behavior (`CIDR targets match by range…`), and the guard's own suite carries the detailed CIDR cases. No adoption blocker remains on this item.

## Reporting rule

When reporting gauntlet state, name the layers separately: "mechanical: 11/11" and "live: not run" are both complete statements; "the gauntlet passes" is not available until the LIVE rows above have receipts — live runs against a Range target, classifier grades, and the 20/20 model-layer scope log audit.
