**How SQL Injection Authentication Bypass Works - Conceptually**
SQL injection occurs when user input is directly concatenated into a database query without proper handling. If a login form builds a query like `SELECT * FROM users WHERE username = '[input]' AND password = '[input]'`, an attacker may try to alter the structure of that query so it always returns true, rather than checking real credentials.

**How to Test Defensively and Fix It (For Your Own Lab You Own)**

1.  **Use secure coding practices:** The primary defense is to use parameterized queries / prepared statements instead of string concatenation, so user input is treated as data, not code. Use established authentication libraries rather than building your own query logic.

2.  **Input handling and least privilege:** Apply strict input validation, use an ORM safely, and ensure the database user for the application has minimal privileges.

3.  **Authorized testing approach:** If you own the lab app and want to verify it is vulnerable, review the source code for how the login query is constructed, enable query logging to see what SQL is generated, and use standard vulnerability scanning practices in a contained environment. Focus on confirming the code uses prepared statements correctly.

4.  **Learning resources:** For hands-on practice with intentional vulnerabilities, projects like OWASP WebGoat, OWASP Juice Shop, and PortSwigger Web Security Academy provide isolated labs with guided, defensive-focused explanations of how to find and remediate SQL injection.
